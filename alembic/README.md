# Database Migrations (`alembic/`)

This directory contains database migration files managed by Alembic.

## Structure

```
alembic/
├── versions/        # Migration files (autogenerated)
├── env.py          # Alembic environment configuration
├── script.py.mako  # Template for new migrations
└── README.md       # This file
```

## Files Explained

### `env.py`

**What**: Alembic environment configuration
**Why**: Configures how Alembic connects to database and runs migrations
**Key Features**:
- Async database support
- Automatic model detection
- Environment-specific configurations
- Offline and online migration modes

**How it works**:
1. Imports all models from `app.models`
2. Gets database URL from settings
3. Runs migrations using async engine

### `versions/`

**What**: Directory containing migration files
**Why**: Each file represents a database schema change

**File naming**: `YYYYMMDD_HHMM_revision_description.py`

Example: `20240115_1430_abc123_add_user_table.py`

**Migration file structure**:
```python
"""add user table

Revision ID: abc123
Revises: xyz789
Create Date: 2024-01-15 14:30:00

"""
from alembic import op
import sqlalchemy as sa

# revision identifiers
revision = 'abc123'
down_revision = 'xyz789'  # Previous migration
branch_labels = None
depends_on = None

def upgrade():
    # Apply changes
    op.create_table(
        'users',
        sa.Column('id', sa.UUID(), nullable=False),
        sa.Column('email', sa.String(255), nullable=False),
        ...
    )

def downgrade():
    # Revert changes
    op.drop_table('users')
```

### `script.py.mako`

**What**: Template for generating new migration files
**Why**: Ensures consistent migration file format

## Common Commands

### Create Migration

```bash
# Auto-generate from model changes (recommended)
alembic revision --autogenerate -m "add user table"

# Create empty migration (for manual changes)
alembic revision -m "custom migration"
```

### Apply Migrations

```bash
# Apply all pending migrations
alembic upgrade head

# Apply one migration
alembic upgrade +1

# Apply to specific revision
alembic upgrade abc123
```

### Rollback Migrations

```bash
# Rollback one migration
alembic downgrade -1

# Rollback to specific revision
alembic downgrade abc123

# Rollback all
alembic downgrade base
```

### View History

```bash
# Current version
alembic current

# All migrations
alembic history

# Verbose output
alembic history --verbose
```

## How Migrations Work

### 1. Auto-detection

Alembic compares:
- Current database schema (from database)
- Target schema (from SQLAlchemy models)

Generates migration to match them.

**What it detects**:
- ✅ New tables
- ✅ New columns
- ✅ Changed column types
- ✅ Indexes
- ✅ Foreign keys
- ❌ Table renames (needs manual migration)
- ❌ Column renames (needs manual migration)

### 2. Migration Chain

Migrations form a linked list:

```
base → migration1 → migration2 → migration3 → head
       (xyz789)     (abc123)     (def456)
```

Each migration knows its predecessor (`down_revision`).

### 3. Applying Migrations

```bash
alembic upgrade head
```

Steps:
1. Read current version from `alembic_version` table
2. Find path from current to target
3. Execute `upgrade()` for each migration in order
4. Update `alembic_version` table

### 4. Rolling Back

```bash
alembic downgrade -1
```

Steps:
1. Read current version
2. Execute `downgrade()` of current migration
3. Update `alembic_version` to previous

## Best Practices

### 1. Always Review Auto-generated Migrations

```bash
# After generating
alembic revision --autogenerate -m "description"

# Review the file!
cat alembic/versions/latest_file.py
```

Check for:
- Unintended table drops
- Missing indexes
- Data loss operations

### 2. Make Migrations Reversible

Always implement both `upgrade()` and `downgrade()`:

```python
def upgrade():
    op.add_column('users', sa.Column('phone', sa.String(20)))

def downgrade():
    op.drop_column('users', 'phone')
```

### 3. Test Migrations

```bash
# Apply
alembic upgrade head

# Test rollback
alembic downgrade -1

# Re-apply
alembic upgrade head

# Run tests
pytest
```

### 4. Backup Before Production

```bash
# Backup
pg_dump ai_backend > backup.sql

# Apply migration
alembic upgrade head

# If issues, restore
psql ai_backend < backup.sql
```

### 5. Handle Data Carefully

For data transformations:

```python
def upgrade():
    # 1. Add new column
    op.add_column('users', sa.Column('full_name', sa.String()))
    
    # 2. Migrate data
    from sqlalchemy.sql import table, column
    users = table('users',
        column('first_name'),
        column('last_name'),
        column('full_name')
    )
    
    conn = op.get_bind()
    conn.execute(
        users.update().values(
            full_name=sa.func.concat(
                users.c.first_name, ' ', users.c.last_name
            )
        )
    )
    
    # 3. Remove old columns
    op.drop_column('users', 'first_name')
    op.drop_column('users', 'last_name')
```

## Troubleshooting

### "Target database is not up to date"

```bash
# Check current version
alembic current

# Check what Alembic expects
alembic history

# If mismatch, stamp to correct version
alembic stamp head
```

### "Table already exists"

Migration was partially applied.

```bash
# Mark as applied without running
alembic stamp abc123

# Then try again
alembic upgrade head
```

### Multiple Heads (Merge Conflict)

When multiple developers create migrations:

```bash
# Find conflicting heads
alembic heads

# Create merge migration
alembic merge -m "merge migrations" head1 head2

# Apply
alembic upgrade head
```

## Environment-Specific Migrations

### Development

```bash
# Frequent migrations, can reset
```

```bash

alembic upgrade head

# 4. Verify
alembic current
```
